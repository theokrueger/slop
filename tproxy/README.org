#+title: tproxy
#+description: A small OpenAI-compatible reverse proxy

tproxy exposes one OpenAI-compatible API and forwards each request to the
upstream configured for the requested model. Clients select a model by its
alias; tproxy authenticates the client, rewrites the model name, adds the
upstream API key, and streams the response back. tproxy is a Linux-only
utility.

* Install

#+begin_src sh
cargo install --path .
tproxy --help
#+end_src

Building requires Rust 1.88 or newer.

The server refuses to start as root. Run it as an unprivileged user; the
systemd user service below is one option.

* Configuration

See [[file:CONFIG.org][CONFIG.org]] for the configuration file, server
options, model metadata, users, and defaults.

* CLI

#+begin_src sh
tproxy                                  # serve using ~/.config/tproxy.yaml
tproxy -c FILE serve                    # serve using FILE
tproxy useradd alice                    # add user, print generated API key
tproxy modeladd                         # interactively add a model
#+end_src

=useradd= and =modeladd= read and rewrite the config file. Comments and
custom formatting in an existing YAML file are not preserved.

The default config path is =~/.config/tproxy.yaml= (or
=$XDG_CONFIG_HOME/tproxy.yaml=). Create it once:

#+begin_src sh
mkdir -p "${XDG_CONFIG_HOME:-$HOME/.config}"
touch "${XDG_CONFIG_HOME:-$HOME/.config}/tproxy.yaml"
#+end_src

Then run =tproxy useradd= and =tproxy modeladd=. Alternatively, use =-c FILE=
with a different config file.

* systemd user service

A user unit is provided at [[file:tproxy.service][tproxy.service]]. It runs
=tproxy serve= using the default config file and restarts on failure.

Install and start it:

#+begin_src sh
mkdir -p ~/.config/systemd/user
cp tproxy.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now tproxy.service
#+end_src

The unit runs =%h/.cargo/bin/tproxy=, where =cargo install --path .= places
the binary. If tproxy is installed elsewhere, edit =ExecStart= first:

#+begin_src sh
systemctl --user edit --full tproxy.service
#+end_src

The service uses the default config path. The service runs as your user, so
that file must be readable and writable by you.

To use a different file, add =-c %h/path/to/tproxy.yaml= to =ExecStart=.

Check the service and follow its logs:

#+begin_src sh
systemctl --user status tproxy.service
journalctl --user -u tproxy.service -f
#+end_src

Logs go to the journal when =server.log= is unset. To keep the service running
after you log out, enable lingering:

#+begin_src sh
loginctl enable-linger "$USER"
#+end_src

Restart after changing the config (model changes require a restart):

#+begin_src sh
systemctl --user restart tproxy.service
#+end_src

Stop and disable it:

#+begin_src sh
systemctl --user disable --now tproxy.service
#+end_src

* API

API requests to =/v1/...= must send =Authorization: Bearer <user API key>=.
Requests are rate limited per user using token buckets. Excess requests
return =429= with =Retry-After=.

Forwarded requests are also capped by a concurrency limit. When full, tproxy
returns =503= with =Retry-After: 1= instead of queueing more work.

| Endpoint                | Behavior                                      |
|-------------------------+-----------------------------------------------|
| =GET /=                 | Public usage dashboard (HTML).                |
| =GET /usage.json=       | Public dashboard data (hourly buckets).       |
| =GET /health=           | Unauthenticated health check, returns =ok=.   |
| =GET /v1/models=        | Lists aliases and model metadata.              |
| =POST /v1/{path}=       | Forwards any =/v1= path.                      |

The model list is built once when the server starts. Restart tproxy after
changing models. Only =POST= requests to =/v1= paths are forwarded. A JSON
body with a top-level =model= field is required, and streaming responses are
passed through unchanged.

Upstream status codes and error responses are passed through, except that
configured upstream API keys are redacted from error bodies, auth-like and
cookie response headers are stripped, redirects are refused, and path
traversal is rejected. The =model= field in the upstream response is not
rewritten back to the alias.

* Usage dashboard

=GET /= serves a self-contained HTML dashboard that graphs request counts per
user and model in hourly bins over the last 30 days. =GET /usage.json= returns
the underlying hourly buckets. Neither endpoint requires authentication, so
anyone who can reach the server can see user names and model usage; restrict
access with a firewall or reverse proxy if that is not acceptable.

A request is counted once it has been forwarded to an upstream, including
upstream error responses. Counters live in memory and are flushed every 5
minutes as append-only updates to =$XDG_DATA_HOME/tproxy_usage.json.log=,
compacted into =$XDG_DATA_HOME/tproxy_usage.json= when the journal grows
large, when expired buckets are pruned, and on shutdown. The default directory
is =~/.local/share=. Both files use mode =0600=, and buckets older than 30
days are pruned.

* Reverse proxy

tproxy speaks plain HTTP. Bind it to loopback and terminate TLS in a reverse
proxy. With Caddy, for example:

#+begin_src caddy
api.example.com {
    reverse_proxy 127.0.0.1:8001
}
#+end_src

Caddy obtains and renews certificates automatically. Keep tproxy bound to
=127.0.0.1=.

* Public deployment

For public exposure:

- Bind to loopback and terminate TLS in a reverse proxy. tproxy speaks plain
  HTTP only.
- Keep the config and log files private. tproxy writes them as mode =0600=
  and warns if the config is accessible by other users.
- Use the generated keys from =tproxy useradd=. Short user keys produce a
  startup warning.
- Remote upstream connections must use HTTPS. Loopback HTTP upstreams are
  allowed unless explicitly overridden.
- Restrict the listening port with a firewall; bind to loopback when possible.
- The usage dashboard at =/= and =/usage.json= is public and exposes user
  names and model usage. Block it at the reverse proxy or firewall if the
  server is reachable by untrusted clients.
- Tune rate limits and concurrency in [[file:CONFIG.org][CONFIG.org]]. Rate-limit
  state is in-memory and resets on restart.
- Upstream API keys are stored in plaintext in the config. Restrict filesystem
  access and back up the config securely.
- Client headers are not forwarded except =accept=, =idempotency-key=, and
  =openai-beta=. The proxy sets =content-type: application/json= itself.
- Request body size and timeouts are not enforced by tproxy; configure them in
  the reverse proxy.

* Pi extension

The extension at =extensions/pi.ts= registers a Pi provider named =tproxy=.
It has no environment-variable configuration. The endpoint defaults to
=http://127.0.0.1:8001/v1= and both the model list and all model metadata come
from =GET /v1/models= through Pi's =refreshModels= hook. The extension has no
hardcoded model IDs, limits, capabilities, or costs.

#+begin_src sh
pi -e ./extensions/pi.ts
#+end_src

Authenticate with =/login tproxy=, then open =/model= once to trigger
discovery. See [[file:CONFIG.org][CONFIG.org]] for Pi =models.json= overrides.
